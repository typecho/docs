# Internationalizing Themes and Plugins

Typecho's interface text is written in Simplified Chinese and translated into other languages through gettext `.mo` language packs (for how site owners use them, see [Interface language](../guide/extend/languages.md)). Text in themes and plugins can be output through the same functions so that it can be translated.

## Translation functions

Three global functions, defined in `var/Typecho/Common.php`:

| Function | Purpose |
|---|---|
| `_t(string $string, ...$args): string` | Returns the translated text; with extra arguments, fills in `%s` and `%d` using `vsprintf()` |
| `_e(string $string, ...$args)` | Same as `_t()`, but outputs directly |
| `_n(string $single, string $plural, int $number): string` | Picks the singular or plural form according to the number and replaces `%d` in it with the number |

```php
<h2><?php _e('最新文章'); ?></h2>
<p><?php echo _t('共有 %d 篇文章', $count); ?></p>
<p><?php _e('%s 发布于 %s', $this->author->screenName, $this->date->format('Y-m-d')); ?></p>
<p><?php echo _n('一条评论', '%d 条评论', $this->commentsNum); ?></p>
```

- The source text is the translation "key", so do not change it casually once it has been published; after a change, existing translations no longer match.
- Do not concatenate variables into the source text; use `%s` / `%d` placeholders so that translators can adjust the word order.
- When there is no language pack, `_n()` uses the plural form if the number is greater than 1 and the singular form otherwise.

When the site owner switches the language, Typecho loads only the core language pack (`usr/langs/<language code>.mo`). Text in themes and plugins that happens to be identical to core text (for example "最新文章" or "评论") uses the core language pack's translation; text that is **unique** to a theme or plugin needs its own translation file.

## Loading your own language file

### Limits of Helper::lang() and I18n::addLang()

Typecho provides `\Utils\Helper::lang($domain)` and `\Typecho\I18n::addLang($file)` for adding language files, but in 1.3.0 neither is suitable for themes and plugins:

- `Helper::lang($domain)` looks for `$domain/lang/<language code>.mo` under the `var/Utils/` directory (the directory that contains `Helper.php`), not in the plugin or theme directory;
- Files added with `I18n::addLang()` **have no effect** on `_t()` / `_e()`: when looking up singular text, if the first language file (the core language pack) does not contain the text, the source text is returned immediately and the files added later are not searched; only `_n()` searches all files in turn. In addition, calling `addLang()` before the core language pack has been loaded causes an error.

### Recommended approach: your own translation function

In the theme's `functions.php` (or in the plugin), read your own `.mo` file with `\Typecho\I18n\GetText` and wrap it in a translation function. The file is chosen according to the site's current language:

```php title="usr/themes/starter/functions.php"
function starter_t(string $string, ...$args): string
{
    static $gettext = false;

    if (false === $gettext) {
        $gettext = null;
        $siteLang = \Typecho\I18n::getLang();
        if ($siteLang) {
            $file = __DIR__ . '/lang/' . basename($siteLang);
            if (is_file($file)) {
                $gettext = new \Typecho\I18n\GetText($file, true);
            }
        }
    }

    $result = $gettext ? $gettext->translate($string, $count) : $string;
    return empty($args) ? $result : vsprintf($result, $args);
}

function starter_e(string $string, ...$args)
{
    echo starter_t($string, ...$args);
}
```

- `\Typecho\I18n::getLang()` returns the path of the core language pack the site currently uses (such as `…/usr/langs/en_US.mo`), and `null` when the site language is Simplified Chinese; take its file name and look for a file with the same name in the theme's own `lang/` directory.
- In templates, use `starter_e('text')` and `starter_t('text')` instead of `_e()` and `_t()`; when there is no matching language file, the Chinese text is output as is.
- Prefix the function names with the theme or plugin name to avoid conflicts with other themes and plugins. In a plugin you can write them as static methods of the plugin class.

Directory structure:

```text
usr/themes/starter/
├── functions.php
└── lang/
    ├── messages.pot   translation template
    ├── en_US.po       translation source file
    └── en_US.mo       compiled file, same name as the core language pack
```

## Generating the .pot

The translation template (`.pot`) lists all source text that needs translating. Extract it from the PHP files with GNU gettext's `xgettext`, adding your own translation functions as keywords:

```bash
xgettext --language=PHP --from-code=UTF-8 \
  --keyword=_t --keyword=_e --keyword=_n:1,2 \
  --keyword=starter_t --keyword=starter_e \
  -o lang/messages.pot $(find . -name '*.php')
```

Run it in the theme or plugin directory. Then:

1. The translator uses a tool such as [Poedit](https://poedit.net/) to create or update `en_US.po` from `messages.pot` and fills in the translations;
2. Compile it to `.mo`:

   ```bash
   msgfmt -o lang/en_US.mo lang/en_US.po
   ```

3. Ship the `.mo` with the theme or plugin. The file name must be the same as the core language pack's (`en_US.mo`, `ja_JP.mo` and so on) for the translation function above to find it.

Typecho's own `messages.pot` is generated by `tools/build_pot.php` in the Typecho source: it scans the string arguments of `_t`, `_e` and `_n` across the whole Typecho directory, cannot be pointed at another directory, and does not recognize custom function names, so themes and plugins should use `xgettext`.

## Notes

- `_t('')` (an empty string) raises an error because of a wrong return type when a language pack is loaded; do not translate empty strings.
- The translation functions only handle literal text. Content from the database (posts, category names, the site name) is not translated.
- Month and weekday names in dates are output by PHP `date()` and do not change with the language.
