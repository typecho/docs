# Development Environment and Front-end Build

Typecho's PHP code needs no compilation; it runs as soon as you change it. The only things that need building are the CSS and JS of the admin panel and of the `classic-22` theme, and the translation template `messages.pot`. The build tools are all in the repository's `tools/` directory.

## Running a development copy

You need PHP 7.4 or later and any supported database (SQLite is the simplest for local development). For the full list of requirements, see [Requirements](../../guide/getting-started/requirements.md).

```bash
git clone https://github.com/typecho/typecho.git
cd typecho

# 命令行安装，使用 SQLite
TYPECHO_SITE_URL=http://127.0.0.1:8000 \
TYPECHO_DB_ADAPTER=Pdo_SQLite \
TYPECHO_DB_FILE=$PWD/usr/dev.db \
TYPECHO_USER_NAME=admin \
TYPECHO_USER_PASSWORD=admin123456 \
php install.php

# 用 PHP 内置服务器运行
php -S 127.0.0.1:8000
```

Running `php -S` directly in the site root (without a router script) is enough: existing files (`admin/*.php`, CSS, images) are served directly, and paths that do not exist are passed to `index.php` in the root, so both front-end URLs and `/action/*` work. For all environment variables of command-line installation, see [Command-line and unattended installation](../../guide/getting-started/cli-install.md).

During development, turn on debug mode in `config.inc.php` so that errors show the full exception message and stack trace:

```php title="config.inc.php"
define('__TYPECHO_DEBUG__', true);
```

`config.inc.php`, the SQLite database file, `usr/uploads/`, and all plugins and themes other than `HelloWorld`, `default` and `classic-22` are in `.gitignore` and are not committed.

## Building front-end assets

### Preparation

`tools/package.json` requires Node.js 18 (`"engines": {"node": "18.x"}`). The dependency `node-sass` compiles a native module during installation, which fails on newer Node.js versions, so use Node.js 18:

```bash
cd tools
npm ci          # 按 package-lock.json 安装
```

### npm scripts

| Command | Source files | Output | What it does |
|---|---|---|---|
| `npm run build_js` | `admin/src/js/*.js` | `admin/js/*.js` | Minifies each file with uglify-js |
| `npm run build_css` | `admin/src/scss/*.scss` | `admin/css/*.css` | Compiles with node-sass (minified output). Files starting with `_` are partials that are included elsewhere and not output on their own; the actual output is `grid.css`, `install.css` and `style.css` |
| `npm run build_css:theme` | `usr/themes/classic-22/static/scss/*.scss` | `usr/themes/classic-22/static/css/*.css` | Compiles the styles of the `classic-22` theme |

`build_css` also combines the small icons in `admin/src/img/icons/` and `admin/src/img/editor/` into sprites, outputs `admin/img/icons.png`, `icons@2x.png`, `editor.png` and `editor@2x.png`, and writes the coordinates into the CSS. Intermediate files for the sprites are cached in `tools/tmp/` (ignored by `.gitignore`).

The build output (`admin/js/`, `admin/css/`, `admin/img/`, the theme's `static/css/`) is committed to the repository, and the release package uses it directly; `admin/src/` and the theme's `static/scss/` exist only in the repository and are removed when packaging. When you change source files, run the corresponding script and commit the source files together with the build output. With a different minifier version, the minified JS may differ from the version in the repository in details such as variable names; this does not affect functionality.

In 1.3.0, the `style.scss` of `classic-22` uses the syntax `@use "…/@picocss/pico/scss" with (…)`, which node-sass does not support: `npm run build_css:theme` writes that line into the output unchanged, and the resulting `style.css` lacks all of Pico CSS's styles and cannot be used. The `classic-22/static/css/style.css` in the repository was compiled with Dart Sass, which supports this syntax (the file starts with the copyright comment of Pico CSS v2.0.6). When you change the theme's styles, compile with Dart Sass instead, or do not commit the files generated by `build_css:theme`.

## Makefile

The targets in `tools/Makefile` must be run in the `tools/` directory:

| Target | What it does |
|---|---|
| `make test` | Runs `php -l` on every PHP file under `var/`, `usr/` and `admin/`, stopping at the first error |
| `make pot` | Runs `php build_pot.php > messages.pot`; see below |
| `make langs` | Clones `typecho/languages`, compiles each `.po` to `.mo` with `msgfmt`, and copies them to `usr/langs/` (deleting the whole `usr/langs/` first). Requires gettext |
| `make update` | Shallow-clones the latest code of `typecho/typecho` from GitHub into `tools/build/`, minifies its CSS and the JS under `admin/js/` with yuicompressor (requires Java), and syntax-checks the PHP files |
| `make package` | Removes development files from the result of `update` and packs it into `build.tar.gz` |
| `make install`, `make upgrade`, `make theme` | Overwrite files in the parent directory with the result of `update` (everything, program files, the default theme) |
| `make all` | `update` + `package` + `clear` |
| `make clear` | Deletes `tools/build/` |

The `update` family of targets always fetches the code from GitHub, regardless of changes in your local working tree. Official release packages are not produced with the Makefile but packaged by GitHub Actions; see [Contributing code](../contributing/index.md#release).

The syntax check is the most commonly used in daily development. CI runs the same command as below, which you can run locally before committing:

```bash
find . -type f -name '*.php' -print0 | xargs -0 -n1 -P4 php -l -n | (! grep -v "No syntax errors detected" )
```

It exits with a non-zero status when it finds any syntax error. Note that it also treats every other message PHP prints as a failure, so run it with the PHP versions CI covers (7.4, 8.0, 8.1, 8.2): on newer PHP versions, `php -l` prints `Deprecated` notices for some deprecated constructs, and the command fails because of them too.

## Generating messages.pot {#pot}

`messages.pot` is the template for interface translations and contains every string in the source code that needs translating. To generate it:

```bash
cd tools
make pot        # 等于 php build_pot.php > messages.pot
```

How `build_pot.php` works:

- It recursively scans **all** `.php` files under the repository root, including those in `usr/themes/` and `usr/plugins/`;
- It uses PHP's tokenizer to find the first string argument of `_t()` and `_e()`, and the singular and plural string arguments of `_n()`; only literal strings are extracted, and text from variables or concatenation is not;
- Identical strings are output only once, and no `#:` source location comments are output.

Because it scans every file under `usr/`, generate it from a clean copy that contains only the plugins and themes shipped with the repository; otherwise text from third-party plugins and themes installed locally ends up in the template as well. `*.pot`, `*.po` and `*.mo` are all in `.gitignore`; `messages.pot` is not committed to the Typecho repository but maintained in the `typecho/languages` repository; see [Translating the Typecho interface](../contributing/translate-typecho.md). For how themes and plugins generate their own translation templates, see [Internationalizing themes and plugins](../i18n.md).
