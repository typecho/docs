# Directory Structure and Namespaces

This section is for developers who modify Typecho itself. This page explains what each top-level directory and entry file in the release package is responsible for, and the rules by which the PHP code is organized into namespaces.

## Top-level directories

```text
typecho/
├── index.php          the single front-end entry point
├── install.php        installer (web and command line)
├── config.inc.php     configuration file generated at install time, not in the repository
├── install/           table creation SQL for the three databases and the install form
├── admin/             admin pages (PHP templates) and admin static assets
├── var/               all PHP classes
│   ├── Typecho/       framework layer
│   ├── Widget/        application layer
│   ├── Utils/         utility classes
│   └── IXR/           XML-RPC library
├── usr/               the site's own content: themes, plugins, uploads, language packs
└── tools/             build scripts for development, not in the release package
```

### index.php

The only front-end entry point, just a few lines long: it loads `config.inc.php` (redirecting to `install.php` if it does not exist), then runs `\Widget\Init::alloc()`, the `index.php:begin` hook, `\Typecho\Router::dispatch()` and the `index.php:end` hook in turn. All front-end URLs, `/action/*` requests, feeds and XML-RPC come in through here. For the full process, see [Request lifecycle](./request-lifecycle.md).

### install.php and install/

`install.php` is a standalone installer. It can install step by step in the browser, or unattended from the command line using environment variables (see [Command-line and unattended installation](../../guide/getting-started/cli-install.md)). It checks the environment, writes `config.inc.php`, runs the table creation scripts, and writes the default options and the first administrator.

The `install/` directory contains the table creation scripts for each database, `Mysql.sql`, `Pgsql.sql` and `SQLite.sql`, and the matching connection parameter forms of the installer, `Mysql.php`, `Pgsql.php` and `SQLite.php`.

### config.inc.php

Generated by the installer. It defines the four constants `__TYPECHO_ROOT_DIR__`, `__TYPECHO_PLUGIN_DIR__`, `__TYPECHO_THEME_DIR__` and `__TYPECHO_ADMIN_DIR__`, loads `var/Typecho/Common.php`, calls `\Typecho\Common::init()`, and then creates the database object and calls `\Typecho\Db::set()`. For the file's contents, see [Configuration file](../../guide/operations/config-file.md). The repository's `.gitignore` ignores it.

### admin/

The admin panel. `admin/*.php` are individual page templates, not classes, and they do not go through the router: the browser requests files such as `admin/manage-posts.php` directly. Each page first does `include 'common.php'`, then `include`s shared fragments as needed (`header.php`, `menu.php`, `copyright.php`, `footer.php` and so on), and calls widgets directly in the page, for example:

```php title="admin/manage-posts.php"
<?php
include 'common.php';
include 'header.php';
include 'menu.php';

$stat = \Widget\Stat::alloc();
$posts = \Widget\Contents\Post\Admin::alloc();
```

`admin/common.php` initializes the environment and prepares the variables `$options`, `$user`, `$security`, `$menu`, `$request` and `$response`; page templates assume they already exist.

Static assets come in two parts: `admin/src/` (SCSS, unminified JS, source icons for the sprite) holds the source files, and `admin/css/`, `admin/js/` and `admin/img/` are the build output. For how to build them, see [Development environment and front-end build](./build.md). The release package leaves out `admin/src/`.

The name of the admin directory can be changed with `__TYPECHO_ADMIN_DIR__`; see [Changing the admin directory](../../guide/operations/admin-dir.md).

### var/

All PHP classes live here, split into four directories by namespace; see below.

### usr/

Files that belong to the site itself:

| Directory | Contents |
|---|---|
| `usr/themes/` | Themes. The repository tracks only `default` and `classic-22` |
| `usr/plugins/` | Plugins. The repository tracks only `HelloWorld` |
| `usr/uploads/` | Uploaded attachments; created on the first upload |
| `usr/langs/` | Language pack `.mo` files; must be created manually |
| `usr/backups/` | Default directory for backup files |

When you install with SQLite, the database file is also placed under `usr/` by default. `usr/` is not replaced when you upgrade Typecho.

### tools/

Development tools, not included in the release package: `build.js` and `package.json` (build the CSS/JS of the admin panel and of `classic-22`), `build_pot.php` (generates the translation template `messages.pot`), and `Makefile` (packaging, syntax checks and so on). See [Development environment and front-end build](./build.md).

## Namespaces

Every PHP file under `var/` declares a namespace, and namespaces correspond one-to-one to directories:

| Namespace | Directory | Responsibility |
|---|---|---|
| `Typecho\` | `var/Typecho/` | Framework layer: the widget base class, routing, plugins, database, request and response, cookies, dates, internationalization, forms, the HTTP client and so on; no blog logic |
| `Widget\` | `var/Widget/` | Application layer: every page, data source and admin operation is a widget, for example `Widget\Archive` and `Widget\Contents\Post\Edit` |
| `Utils\` | `var/Utils/` | Framework-independent utilities: `Helper`, `Markdown`, `HyperDown`, `AutoP`, `PasswordHash`, `Upgrade` |
| `IXR\` | `var/IXR/` | XML-RPC server and client, used by `Widget\XmlRpc` and pingbacks |
| `TypechoPlugin\<plugin name>\` | `usr/plugins/<plugin name>/` | Plugins; see [Plugin structure and lifecycle](../plugin/structure.md) |

### var/Typecho

| Location | Contents |
|---|---|
| `Common.php` | The autoloader, the `_t()`/`_e()`/`_n()` translation functions, the `Typecho\Common` static utility class and the version number `Common::VERSION` |
| `Widget.php`, `Widget/` | The widget base class, widget-level request and response (`Widget\Request`, `Widget\Response`), and helper classes for forms, pagination and so on (`Widget\Helper\*`) |
| `Router.php`, `Router/` | The router, the route rule parser `Router\Parser`, and `Router\ParamsDelegateInterface` |
| `Plugin.php`, `Plugin/` | Hook registration and invocation, `Plugin\PluginInterface` |
| `Db.php`, `Db/` | The database object, the query builder `Db\Query`, and the database adapters `Db\Adapter\*` |
| `Request.php`, `Response.php` | The global HTTP request and response objects |
| `Http/` | The outbound HTTP client `Http\Client` |
| `I18n.php`, `I18n/` | Reading gettext `.mo` files |
| `Cookie.php`, `Date.php`, `Config.php`, `Validate.php`, `Feed.php` | Cookies, time zones and dates, parameter objects, form validation, RSS/Atom generation |

### var/Widget

The application layer is split into directories by area:

| Location | Contents |
|---|---|
| `Base.php`, `Base/` | `Widget\Base`, the base class of all application widgets, plus the base classes of the four kinds of data rows, `Base\Contents`, `Base\Comments`, `Base\Metas`, `Base\Users`, and `Base\Options` |
| `Contents/`, `Comments/`, `Metas/`, `Users/` | List, edit and admin management widgets for each kind of data |
| `Options/`, `Plugins/`, `Themes/` | Settings pages, plugin management, theme management |
| `Archive.php` | The main entry point for front-end pages; `$this` in templates |
| `Init.php`, `Options.php`, `User.php`, `Security.php`, `Menu.php` | Initialization, site options, current user, tokens, admin menu |
| `Action.php`, `ActionInterface.php` | The dispatcher and interface for `/action/<name>` |
| `Feed.php`, `Feedback.php`, `CommentPage.php`, `XmlRpc.php`, `Service.php`, `Upload.php`, `Backup.php`, `Upgrade.php`, `Login.php`, `Logout.php`, `Register.php`, `Ajax.php`, `Stat.php`, `Notice.php`, `ExceptionHandle.php` | Independent features, one per file |

For how widgets work, see [The widget component model](./widget.md).

### Autoloading and legacy class names

The autoloader is registered when `var/Typecho/Common.php` is loaded (the `spl_autoload_register()` at the top of the file); it does not depend on Composer:

- A namespaced class `\A\B\C` is loaded from `var/A/B/C.php`; `\TypechoPlugin\X\Y` is loaded from `usr/plugins/X/Y.php`;
- Legacy class names written with underscores are mapped to the new class names and an alias is created automatically: `Typecho_Foo_Bar` → `\Typecho\Foo\Bar`, `Widget_Foo` → `\Widget\Foo`, and any other `Foo_Bar` is treated as the plugin class `\TypechoPlugin\Foo\Bar`;
- Legacy class names that do not follow these mechanical rules (such as `Widget_Abstract_Contents` → `\Widget\Base\Contents` and `Helper` → `\Utils\Helper`) are listed explicitly in the constant `__TYPECHO_CLASS_ALIASES__` in `var/Widget/Init.php`.

For the full mapping, see the [legacy class name table](../reference/class-aliases.md). For the requirement to keep these legacy class names working when you modify core code, see [Coding style](./coding-style.md#aliases).
